### 2.1 内容固定范围（用户确认，2026-11-11，选择 A）

普通字段沿用 D-016/D-018：派生仅选定业务 Revision，Source-backed 读取来源该版次的当前普通字段，首次 COW
以首次相关修改前快照固定。附件与关系沿用 R19：固定为派生时状态，来源后续变化不得改变该派生基准；关系目标的全部内容不递归冻结。目标合法的本地修改仍由业务
BC 管理。**附件与关系不参与 Compare/Merge（D6，2026-11-12 用户裁定）**：Merge 只比较与合并普通字段，固定基准不被 Merge 改写。

首次物化必须将普通字段快照与目标派生时固定的附件、关系事实组合后，由 BC
整体校验；不得用来源事件中的较新附件、关系覆盖派生基准。固定事实缺失时不得回退到来源当前值或宣称物化完成。存储、回读与恢复机制仍属实现待办，不在
LightTrackerItem 增加业务内容副本。

确认依据与备选方案见[一致性修正记录](../archive/reviews/2026-11-11-consistency-reconciliation.md)，验收见 SCN-072。

### 3.1 双表索引与版次成员

**状态：Draft（用户授权实施的兼容切片；尚未纳入正式基线）。**

LightTrackerItem 保存当前版次与有效内容来源，并拥有按自身 `Revision` 标识的 `LightTrackerItemRevisionEntity`
。单版次只有初始成员，多版次至少有当前成员；成员记录版次是否已纳入索引。业务内容及历史快照仍由业务 BC
持有。每次从持久化重建根，当前版次必须存在于成员集合。

| 生命周期动作       | 当前索引与版次成员                                                                                                                                                                                                                              |
|--------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 原生创建或派生认领 | 同事务写根及初始版次成员；业务来源版次不拿来创建额外成员。派生使用同一聚合仓储的 `claimFamily`，按工作集和 CommonId 原子认领并保留先写入的聚合。公共查询视图（`air_inst_common`）由业务 BC 消费 `TrackerItemsIndexedEvent` 自行投影，最终一致。 |
| 普通编辑或 COW     | 不创建新业务版次；COW 仅切换当前有效内容来源。                                                                                                                                                                                                  |
| 显式升版事件       | 更新根的自身版次；保留旧成员并新增新版次成员。本地承载时同步更新来源版次。来源升版触发依赖变体的 COW，依赖变体不跟随升版。                                                                                                                      |
| 软删除或恢复       | 监听变体自身的生命周期事件，在独立事务锁定并保存聚合；只改变当前索引的 `deleted` 状态，不删除或新增版次成员。                                                                                                                                   |
| 彻底删除           | 删除当前索引及全部版次成员，继续由业务永久删除事件驱动。                                                                                                                                                                                        |

仓储将根存入 `air_ws_items_index`，成员存入 `air_ws_items_revision_index`；旧设计中的 V4 物理表 `light_tracker_items`
不再是生产读写对象。两表使用独立雪花行主键；根按 `local_id` 寻址，成员按 `(local_id, revision)` 去重。旧表 `has_copied` 按
0/1 映射物化状态。当前索引的 Tracker 范围来自所属 Tracker；业务子类与工作空间由 LightTrackerItem 从其所属 Tracker 带入（
`sub_class_id` / `work_space_id`），不再读取公共摘要，旧数据由 Tracker 列回退。当前索引 `air_ws_items_index.flags` 只表示软删：
`0` 未删除、`1` 已删除；新活动行明确写 `0`，历史空值按未标记处理。不改旧表列，也不将此口径套用到版次索引的同名列。树、审计及其他有效状态字段仍沿用原兼容范围。版次索引本身不存来源指针或内容快照。

业务 BC 与 LTI 继续各自提交。LTI 消费 `BusinessObjectUpdateEvent` 时只处理自身明确的 +1
版次变更：锁定根，前置版次未就绪时保留失败供重投，已处理事件不重复新增成员。物化与版次更新由 LTI
自身执行，仓储只写当前变更与新成员。此切片尚未开放业务侧升版入口；撤销最新版次、版号能否重用及存在历史来源依赖时的处理仍待裁定。仅比较版号的重投判断不适用于撤销后重用版号。

本仓库只支持从空库执行当前 schema；已有库不自动迁移，也不保留旧 V4 索引兼容。存量环境需要单独的一次性迁移与核对方案，不得把历史脚本重新放回当前
schema。

### 删除与来源保留（QUESTION-006）

来源必须先软删。软删与修改前快照及 `BusinessObjectUpdateEvent` 同事务提交；已有 Source-backed
派生项监听后，使用删除前快照写入自己的业务对象，再在独立事务把索引切换为 Local-backed。软删不会移除来源历史。附件和关系已有的派生时固定规则不变。ALM
同时在业务事务中发布 `BusinessObjectDeleteEvent`
。工作集端按事件标识找到该变体，在业务行锁保护下核对最新实际状态，再锁定并保存其索引，迟到的软删事件不会覆盖恢复。标记仅作用于该变体；派生项通过物化保持有效。普通
Tracker 列表、派生分页过滤软删索引，家族占用及永久删除守卫仍识别这些行。

永久删除在来源行锁下先校验已软删，再只读检查是否还有索引以该对象为内容来源。存在依赖时返回 `409 Preparing`
，不删除来源或快照；已失败但仍未切换的依赖同样阻止删除，不把失败当成完成。创建和扩展均普通读取来源，ALM 永久删除与派生步骤通过可串行化事务协调竞争。派生跳过读到的已软删来源。全部依赖不再指向来源后，
`delete2` 才清除来源及其业务快照，已物化派生项保留原 LocalId、自身版次和可编辑性。此规则按实际依赖保留，不按固定天数淘汰。

物化请求与收据原子持久化；技术投递失败不吞掉源事件，可以重投。业务物化仍按既有契约区分失败终态；缺失历史显式失败，不能用当前值代替。验收见 [CowAcceptanceTest](../../../deploys/src/test/java/bootstrap/CowAcceptanceTest.java)。

## 4. 双态契约与状态判定

| 状态              | 权威判定               | 必须同时成立的一致性约束                                                           | 内容来源                                                              |
|-------------------|------------------------|------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| **Source-backed** | `materialized = false` | `sourceLocalId` 指向外部实际有效内容来源；`sourceRevision` 为该来源的业务 Revision | 由 `sourceLocalId` + `sourceRevision` 解析到的实际内容拥有者（D-013） |
| **Local-backed**  | `materialized = true`  | `sourceLocalId = localId` 且 `sourceRevision = revision`                           | 自身；业务 BC 按 `localId` 重建                                       |

约束：

- **`materialized` 是物化状态的权威字段**，属 LightTrackerItem 的正式状态契约；`sourceLocalId != localId` **不再**
  作为唯一权威物化状态定义，只保留为身份/来源一致性约束。
- 三类字段（`materialized`、`sourceLocalId`、`sourceRevision`）必须在**同一次 LightTrackerItem 聚合状态变更**
  中一致更新；状态字段不得由外部服务绕过聚合行为独立修改。
- 若三者不一致（例如 `materialized=true` 而来源仍指向外部），属**元数据一致性缺陷**，不是第三种业务状态，须由修复流程收敛。
- 只有两个**业务状态**；`Materializing` 是技术运行态，**不纳入领域枚举**（D-010）。
- `SourceLocalId` 只表达当前有效内容来源，不承担历史派生关系（D-012/D-018）。
- 未物化不等于不存在（INV-029）；Query 调用方不感知物化过程（D-008）。

## 5. LocalId 契约（K2′，用户确认）

- **派生时预分配全局唯一 `LocalId`**（D-008 第 7 条）：即使尚未物化，变体已拥有稳定身份。
- **首次物化必须复用该 `LocalId`**：物化前后不得出现两个变体身份。
- **COW 不改变** `LocalId` / `CommonId`（INV-040）。
- **不强制业务 BC 的存储主键等于 `LocalId`**；但业务 BC **必须能够通过稳定 `LocalId` 定位或创建对应业务变体**（跨 BC
  解析能力是契约要求）。
- **不持久化额外内容指针**，不持有完整业务字段：内容定位由业务 BC 负责，避免形成第三份真相。

## 6. 首次物化协议

**触发**：来源业务对象修改保存成功后发出的来源变更事件（携带修改前不可变完整快照）。

**目标确定**：Handler **消费时**查询满足条件的 **Source-backed**（`materialized = false`）且 `sourceLocalId`/
`sourceRevision` 匹配的 LightTrackerItem（D-017、INV-050）；命中多少个就物化多少个（扇出，INV-044）。

**内容**：普通字段取事件关联的**修改前不可变快照**（D-010、INV-034/037）；附件与关系取目标派生基准，遵循 §2.1。

**步骤**（每次物化一条变体）：

1. 校验该变体仍为 Source-backed 且 `sourceLocalId`/`sourceRevision` 匹配；若已 Local-backed 则跳过（幂等，INV-038/039）。
2. 业务 BC 按 §2.1 组合普通字段快照与目标的附件、关系事实构建完整聚合，**使用预分配的 `LocalId`**，按目标 BC 规则整体校验后保存。
3. 保存成功后，在**单个 LightTrackerItem 聚合事务**中同时更新：`materialized = true`、`sourceLocalId = localId`、
   `sourceRevision = revision`。
4. 记录物化完成事实；完成记录/事件不得早于实际保存成功（D-012 技术约束）。
5. 若目标 BC 拒绝保存：**不切换状态**（`materialized` 保持 false），按事件重试或告警；不得伪造物化完成。

**完成标志**：业务聚合保存成功 **且** LightTrackerItem 切换成功（`materialized=true`）。只满足其一即为**未完成**（双事实，见
§7）。

## 7. 跨 BC 一致性（双事实，K3′ 用户确认）

LightTrackerItem 与业务聚合是**双事实**：前者持身份/来源/物化状态/定位，后者持完整内容与不变量。两者按 ID 引用，不组合；
**不要求业务 BC 与 LightTrackerItem 在同一数据库事务提交**（ADR-0002）。

| 失败模式                                | 处理                                                                                                           |
|-----------------------------------------|----------------------------------------------------------------------------------------------------------------|
| 业务保存成功、LightTrackerItem 切换失败 | **不回滚已保存的业务内容**；已记录故障不启用业务恢复；未完成技术投递策略见下方实现差距；对外不得宣称「已物化」 |
| 业务保存失败                            | **不切换状态**；记录确定失败并保持 Source-backed，不重做已记录业务终态                                         |
| 事件重复投递                            | 幂等：`materialized=true` 的变体直接跳过，不生成第二个有效物化结果（INV-038）                                  |
| 事件乱序（旧事件晚到）                  | 已 Local-backed 不再被覆盖（INV-039）；未物化时以首次相关修改的快照为准（INV-037）                             |
| 物化期间被查询                          | 普通字段允许暂时读到来源修改后内容；附件与关系保持 §2.1 的派生基准，不随来源变化；物化切换后返回本地内容       |
| 三字段不一致                            | 按元数据一致性缺陷修复（补齐切换），不引入第三种状态                                                           |

**一致性方案**：来源变更与其快照、发布记录提交后，SK 发出物化请求；目标 BC 独立提交并发布结果，SK 再保存 LTI。TC-002
禁止跨聚合写事务。面向业务的 COW
恢复入口已移除；技术事件重投与已记录业务终态的重做不是一回事，未决项见 [实现边界](../07-implementation.md)。

## 8. 与 Merge（T1）和绑定（T2）的衔接

- **未物化目标参与 Diff**：不要求先物化（D-019）。
- **Merge 修改未物化目标**：业务 BC 构建目标聚合并正常 Save（D-019、INV-062），保存成功后发布结果事件；SK 消费
  `MergeAppliedEvent` 后在**独立事务**按既有 COW 状态切换行为更新 LightTrackerItem（`materialized`、`sourceLocalId`、
  `sourceRevision` 同步切换）。
- **Merge 不直接写** `materialized`、`sourceLocalId`、`sourceRevision`、`revision`：只能经由既有 COW/`MergeAppliedEvent`
  事件机制；不同聚合不共享写事务。
- **MergeCheckpoint 不以 `materialized` 作为确认依据**：仍使用既定的双侧比较证据与业务 Revision 语义（T1 CK-3/CK-4）。
- **Tracker 删除**继续检查关联 TrackerItem（T2、POL-014），不因状态字段改变生命周期政策；绑定移除不影响变体身份与来源字段。
