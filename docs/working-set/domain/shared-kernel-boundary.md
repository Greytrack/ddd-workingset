# Working Set Shared Kernel 边界

**状态：Draft（包含 Confirmed 组织约束与 Candidate 交互设计）**

## 已确认约束

`AC-001`：Working Set 位于企业 Shared Kernel 内，为 GateFlow、ALM、DQA、PLM 四个业务 BC 提供公共工作集能力；Shared Kernel 还包含 Privilege、Workflow、Class Hierarchy。该定位不在本项目的方案空间内。

可视化见 [Shared Kernel 与四个业务 BC](../diagrams/shared-kernel-context-map.md)。直接依据见 [证据登记](evidence-register.md) 的 `USER-ARCH-2026-11-09`。

## 设计原则

**四 BC 合并职责已由用户确认。** 对于参与 Working Set 的 ALM、PLM、GateFlow、DQA 对象，各业务 BC 统一负责校验整个业务对象并决定是否提交，各自保留专有校验规则。Working Set 负责用户的合并选择、执行协调和结果记录。确认依据为本对话中用户明确答复「统一采用这个职责划分，各 BC 保留自己的校验规则」。具体对象接入范围与端口协议继续按场景细化。

> Working Set Shared Kernel 管理跨四个业务 BC 共同成立的工作集语义和通用机制；业务对象的专有状态机、字段规则和整体合法性仍由对应业务 BC 拥有。

因此，共用 API 只能统一协作语言、证据和结果结构，不能假定 Requirement、Part、GateFlow 对象和 DQA 对象具有相同领域行为。

## PLM Part 的接入范围（用户已确认）

Part 通过共享 Tracker 接入 Working Set。PLM 在默认工作集下独立管理 Part，其他工作集可纳入该共享 Tracker 查看共享数据。Part 不参与工作集派生、比对和合并。确认依据为本对话用户对 Part 共享 Tracker 定位的明确说明。

本文以「承载 Part 的共享 Tracker」表达对象和集合的关系。此确认替代阶段 3 从历史 V4 材料推演的「普通 Part 非受管/未接入」分支。历史材料保留为来源证据。四 BC 的统一校验与提交职责适用于各自实际支持的业务变化，Part 的工作集合并能力不适用。

## GateFlow Process 与版次（用户已确认）

用户在本对话明确说明 GateFlow 需要按其 BC 业务语义单独讨论。

- Process 是 GateFlow 最重要的聚合，一个 Process 有多个版本。
- 每个版本容纳多个具有业务语义的离散元素。用户已确认固定为四类：过程元素业务对象、裁剪问题、裁剪答案、合规映射。
- GateFlow 工作集不纳入 Part 等共享 Tracker，内容范围限定为上述四类。
- GateFlow 的一个版次对应一个工作集，工作集父子链条构成版次链路。
- GateFlow 支持版次内容替换，可以从历史版次取出全部内容数据，替换叶子节点中的草稿版次内容。
- 用户已确认，V3 中独有而 V1 中没有的流程元素，在以 V1 替换 V3 后退出 V3 当前内容，替换后的内容完整对应 V1。旧元素清理和外部引用策略继续设计。
- 用户已确认，V3 在替换准备期间继续使用当前完整内容并允许编辑，全部准备成功后整体切换。期间编辑可以被历史内容覆盖，符合用户确认的业务语义。准备失败时维持当前内容及已保存编辑。事务实现、恢复与切换瞬间的并发提交机制继续设计。

以上对应关系适用于 GateFlow。本阶段仅讨论这四类对象与 Working Set 的身份、范围、版次和内容替换协作。四类对象内部的细节业务逻辑由 GateFlow 自身设计，本轮不展开。草稿资格和版本业务规则由 GateFlow 拥有，工作集通用范围机制的协作契约继续设计。

历史输入 [V4 内容替换](../../../pre-design/workingsetModel-V4/06-workingset-content-replacement.md) 已讨论保持 WorkingSetId/parentId、重建内容身份与共享内容保留等候选实现。本轮用户确认的是上述能力和对应关系，V1 → V2 → V3（草稿）中，以 V1 内容替换 V3 时，用户已确认保留 V3 版次身份、工作集 ID 及父级 V2。具体内部身份与跨边界引用的实现继续设计。历史方案中的共享内容处理分支不适用于本轮已确认的 GateFlow 对象范围。场景见 [GateFlow 草稿内容替换](../scenarios/shared-kernel-boundary-scenarios.md#gateflow-草稿版次内容替换)。

## DQA 共享查看范围（用户已确认）

DQA 是质量体系建设的一环，自行管理业务逻辑。其 Tracker 全部为共享 Tracker，Working Set 的唯一结合点是将共享 Tracker 纳入查看。DQA 的 Tracker 和业务对象不参与工作集比对、合并，也不进入非共享派生路径。

用户明确列出的对象包括：技术评审任务、过程保证任务、问题报告 PR、检查单、检查单模板、批注、评审文档（被评审对象）、评审报告（评审产物）。这里记录八类对象范围，具体 Tracker 与类型的数量对应关系按现有模型处理。

确认来源为本对话中用户对 DQA 接入范围的明确说明。此前统一的业务 BC 校验/提交职责按实际能力适用，DQA 以共享查看接入，业务对象的修改及专有规则由 DQA 管理。共享 Tracker 及其 Item 的修改归属默认工作集，适用下述已确认通用规则。

## Item 创建入口与归属（用户已确认）

子工作集可在其已有非共享 Tracker 下原生新建 Item。对共享 Tracker，从子工作集入口新建的 Item 实际在默认工作集创建，通过共享 Tracker 纳入的工作集可查看。子工作集禁止创建 Tracker。Working Set 应解析实际创建归属，再交所属业务 BC 校验并创建合法对象。公共能力的操作入口与生命周期归属分别表达。

场景见 [子工作集新建 Item](../scenarios/core-scenarios.md#子工作集新建-item-与-tracker-边界)。子工作集新增 Item 回并父工作集已获用户确认，允许通过用户合并决定在父工作集创建对应 Item，由目标业务 BC 校验并提交。家族身份分配、创建事实同步与去重协议待设计。各 BC 暴露的具体创建入口依其实际接入合同确定。

## 比对与合并的关系准入（用户已确认）

比对、合并仅允许直接父子工作集之间进行，父 → 子、子 → 父两个方向均支持新增、删除、修改。接收方根据用户的合并选择产生对应新增、删除、修改，由接收方所属业务 BC 校验并决定提交。删除合并属于 Item 存在性决定，不是移除 Tracker 绑定。用户进一步确认，无论接收方发生什么变动，均以用户合并决策为准，不因接收方变化提示冲突；包括接收方已修改对象时仍按选择执行删除。此优先级与业务 BC 合法性校验共同适用，见 [决策优先政策](facts.md#合并决策优先于接收方变动已确认业务政策)。兄弟工作集以及不相邻的祖先/后代工作集不允许直接比对或合并。具体对象还应具备相应能力，PLM Part 与 DQA 的共享查看范围不进入这些路径。

该规则来自本对话用户的明确确认，见 [POL-004 / FACT-007](facts.md) 及 [双向合并场景](../scenarios/core-scenarios.md#直接父子双向合并新增删除修改)。GateFlow 从历史版次取内容替换叶子草稿，使用其独立的内容替换合同，保留已确认的 V1 内容替换 V3 场景。

## 共享 Tracker 的修改与绑定（用户已确认）

共享 Tracker 自身的修改，以及其内部 Item 的新增、修改，都发生在默认工作集。子工作集可以作为操作入口，但不会形成子工作集独有的共享内容；所有绑定该共享 Tracker 的工作集同时可见。共享 Tracker 一旦绑定到某工作集，就不允许从该工作集移除。

来源为本对话用户明确确认的两条共享规则。业务内容仍由所属 BC 校验和提交。用户随后确认统一政策：Tracker 一旦加入某个子工作集，无论共享还是非共享，后续均不允许移除，与是否包含 Item 或本地修改无关，见 [POL-006](facts.md)。此确认不裁定对象删除或整个工作集删除。Sharing Mode 的创建规则与不可变性见下节。验收场景见 [SCN-002](../scenarios/core-scenarios.md#scn-002-引用-shared-tracker)。

## 分类配置与 Tracker 共享特性（用户已确认）

分类配置的共享特性是固定出厂设定，不允许修改，与是否已创建 Tracker 无关。Tracker 的共享特性在创建时确定，后续不可修改。分类配置约束创建时的可选值：

| 分类配置 | 创建共享 Tracker | 创建非共享 Tracker |
| --- | --- | --- |
| 共享 | 允许，唯一选择 | 禁止 |
| 非共享 | 允许 | 允许 |

来源为本对话用户明确说明，记录为 [POL-003](facts.md)，验证见 [创建约束场景](../scenarios/core-scenarios.md#tracker-共享特性的创建约束)。分类配置的“非共享”不能解释为强制所有 Tracker 非共享。创建能力应遵守分类配置约束，既有 Tracker 保持其确定的共享特性；分类共享特性的变更问题已由用户确认关闭，跨能力校验协议仍待设计。此处仅记录已讨论的共享属性，不扩展为分类其他属性的变更规则。

## 候选职责边界

以下是阶段 3.0 的评审起点，不是已确认契约。

| 候选能力 | Working Set Shared Kernel 的通用责任 | 业务 BC 的专有责任 | 仍需确认 |
| --- | --- | --- | --- |
| `create` | 建立工作上下文、范围选择、稳定身份映射和可恢复任务候选 | 校验并创建合法业务对象或暴露已有对象事实 | `create` 是创建 Working Set、Tracker 还是业务 Item；事务返回语义 |
| `extend` | 扩展已发布范围、保留幂等身份并发布范围事实候选 | 提供新增业务对象事实，处理本 BC 的准入规则 | 扩展粒度、拒绝后的部分成功和补偿 |
| `resolve` | 按 Working Set、Tracker 和身份解析有效 Variant／Source Cut 候选 | 授权并返回本 BC 的权威内容、生命周期和历史 | 权限、无权／不存在／已删除的错误语言 |
| `diff` | 固定有向上下文、对齐身份、组织通用 Difference 证据候选 | 定义字段语义、相等规则、不可比较字段和脱敏 | 通用差异模型能覆盖哪些 BC；扩展字段合同 |
| `merge` | 保存决定、编排应用、记录 Apply Result／Checkpoint 候选 | 校验并提交目标业务变化，保护聚合整体不变量 | BC 拒绝、部分成功、重试、事件和事务边界 |

## 候选协作方式

1. **稳定 Port／Adapter**：Working Set 定义最小 Published Language，各 BC 提供适配器。优点是同步校验清晰；风险是接口膨胀和 Shared Kernel 反向依赖所有 BC。
2. **命令与事实事件**：Working Set 发布意图或范围事实，BC 独立处理并返回结果事实。优点是解耦；风险是中间态、补偿和用户等待语义复杂。
3. **混合方式**：解析、比较读取走稳定查询端口，目标写入走 BC 命令，跨聚合修复走事件。它最符合现有候选场景，但必须逐能力证明，不能默认采用。

“共享一个通用业务对象 Map 并由 Working Set 直接写所有字段”不是默认候选，因为它会绕过四个 BC 的专有模型。

## 阶段 3.0 必须回答

- 哪些 create／extend／resolve／diff／merge 名称是稳定业务能力，哪些只是示意 API？
- 每个 BC 向 Working Set 暴露的最小公共语言是什么？
- BC 拒绝 Merge Decision 时，共享内核如何表达未执行、冲突、部分成功和可重试？
- Privilege、Workflow、Class Hierarchy 与 Working Set 的交互是共享模型、同步端口还是事实事件？
- Shared Kernel 的模型变更由谁批准，四个 BC 如何版本兼容？

在这些问题闭合前，不确认跨 BC 接口签名，也不据此选择 Working Set 内部聚合方案。

## 阶段 3：责任模式正式比较（Candidate）

本轮授权覆盖候选边界、交互和业务契约的联合推演，不代表逐层设计获批。评审及待裁定清单见 [阶段 3 报告](../reviews/2026-11-09-stage-3-architecture-review.md)，推演见 [边界场景](../scenarios/shared-kernel-boundary-scenarios.md)。

| 模式 | 真正可行的形式 | 收益 | 成本、反例与放弃条件 |
| --- | --- | --- | --- |
| A 公共语义协调 | SK 管范围、身份、证据和进度；BC 完成所有内容读取、比较、修改 | 模型所有权清楚，适配器独立演进 | 每个 BC 重复比较基础设施；若纯身份查询也必须调用 BC，会放大依赖和延迟；需批量端口 |
| B 通用修改引擎 | BC 显式委托有限字段与复制能力；BC 控制事务入口，锁内校验整体并提交，引擎不得直接绕开聚合写表 | 同构且声明式约束的类型可复用复制和差异执行 | 校验后再通用写入存在竞态；业务副作用、状态机与字段耦合无法完整委托时必须退出。若执行权仍在 BC，收益主要是共享执行库而非 SK 获得业务所有权 |
| C 按能力分工 | 身份定位由 SK；内容读取/语义比较由 BC；SK 组织证据和决定；BC 校验并提交；SK 记录结果和确认 | 复用工作范围和合并协议，保留专有行为 | 多方结果恢复、能力协商和契约版本复杂；如果要求跨 BC 全部对象原子提交，则本候选不足 |

四 BC 的合并校验与提交职责已按上述设计原则确认。责任模式 C 的其余能力分配仍为推荐，A 保留为语义比较等能力的委托型备选。B 若采用通用执行库，也必须遵守由业务 BC 校验整个对象并决定提交的已确认边界。企业归属与 DDD Shared Kernel 的模型治理关系仍待明确。

### 候选业务契约（不是最终 API）

所有写请求携带调用者与授权上下文、能力/模式版本、请求身份与载荷指纹；同键不同载荷返回冲突。重试由发起流程负责，业务 BC 必须能按操作身份查回已提交结果；未知结果不得当作未执行再写。合并批次按 [B08 用户裁定](../scenarios/shared-kernel-boundary-scenarios.md#b08-部分成功与批次重试) 允许部分成功，批次重试仅处理未完成项。已成功项保留实际结果，源端再次变化也跳过该成功项。

| 能力/目的 | 调用方与责任所有者 | 输入事实与输出/失败 | 历史、并发、一致性、恢复 |
| --- | --- | --- | --- |
| create 工作范围 | BC 应用 → SK 范围流程；BC 创建对象是另一个能力 | 来源选择、范围意图 → 准备中/已发布/拒绝；不自动创建业务对象 | 固定来源；范围版本 CAS；准备可重试，最终发布原子；失败释放准备占用，不能自动删除已创建业务对象 |
| create 业务对象并纳入 | BC 应用创建并提交合法对象，再请求 SK 纳入 | 业务身份、已提交事实、目标范围 → 内容已建且纳入待完成/已纳入/拒绝 | BC 提交内校验和授权；SK 以事实身份去重。纳入失败需重试或显式取消纳入，非跨 BC 原子承诺 |
| extend 扩展范围 | BC 应用 → SK；BC 提供准入与固定内容能力 | 现范围版本、增量选择、切点 → 新范围/准备中/冲突/不支持类型 | 新成员稳定身份，Source Cut 保留凭据；准备最终一致，发布原子；取消释放未发布占用，已发布范围不回退 |
| resolve 有效定位与读取 | BC/查询调用者 → SK 定位，再由 BC 授权读取 | 工作集、CommonId/LocalId 身份、可选固定证据 → 定位结果及经授权内容 | SK 可独立定位但不能独立承诺内容可读；范围版本和内容证据分别返回。无权、未纳入、不存在、已删、历史不可用、处理中分开；仅内部可信接口披露具体原因，对外按权限政策脱敏 |
| diff 有向比较 | 用户经应用 → SK 组织，BC 提供语义比较 | 双侧冻结成员/内容证据、方向、字段模式版本 → Difference/不可比较/无权/历史不可用 | 无权字段不输出值；无差异也需证据；请求可按证据复用。任一必需历史缺失不退回当前值；Source Cut 与业务 revision 不等同 |
| merge 应用并确认 | 用户决定 → SK；目标 BC 唯一提交业务内容 | Difference 身份、审阅证据、存在性及字段决定、操作身份 → 分项结果/拒绝/冲突/未知 | 按 [B09 用户裁定](../scenarios/shared-kernel-boundary-scenarios.md#b09-接受字段时取源端最新值)，后端执行时读取已选 ACCEPT 字段的权威源最新值。审阅证据与执行所读版本分开保留。执行时重授权，目标 BC 校验整体后提交。候选协议由 BC 原子提交内容与可恢复回执，SK 收敛进度并以 CAS 保护 Checkpoint。审阅后、提交前目标同一 ACCEPT 字段变更时，校验通过即覆盖该字段，不提示冲突。单字段不可读仅为极端兜底，该条 Requirement 保持未完成，批次继续下一条。执行期间的并发控制仍待细化 |

按 [KEEP_TARGET 已确认场景](../scenarios/core-scenarios.md#keep_target-的已处理确认)，保留目标内容可设置 markAsMerged=true，决策结果写入 MergeCheckpoint，双侧版次未变时下一次比对不显示该差异。这里的版次已确认为显式升级的业务 revision。普通修改只增加乐观锁 version，双侧业务版次均未变时，已处理差异继续隐藏。比对由用户主动发起。任一侧显式升级版次后，用户再次比对时旧 MergeCheckpoint 对该新版本组合过时，之前合并过或未合并过的字段均重新比对，显示仍存在的差异。DEFER 不得完成整条确认仍为候选规则。validation 的预览成功不是 apply 许可。有数据变更的路径先记录决定再应用，回读实际成功结果后推进 Checkpoint；KEEP_TARGET 路径记录无内容变更的决定与处理确认。结果丢失时仅查回/重投同操作；已成功部分撤销需新业务命令，不能宣称补偿等同事务回滚。

Privilege 提供身份/授权事实，业务 BC 裁决专有业务操作，SK 裁决范围操作；Workflow 提供流程事实，BC 解释其业务含义；Class Hierarchy 提供分类身份和版本，SK 验证范围适用性，BC 验证字段规则。提供方不可用返回依赖不可用，不能默许操作。是否允许缓存授权、撤权时效和规则版本保留均待确认。
