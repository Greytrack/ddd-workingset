## 对象范围与证据限制

ALM Requirement 是 V4 已使用的受管对象例子；其具体字段及状态规则未确认。PLM Part 必须分两支：历史 V4 08 §5、§6 D03/D05 将普通 Part 作为非受管对照；若未来声明某类 Part 受管才进入以下工作集流程，不能以 AC-001 推翻此前输入。GateFlow/DQA 均使用“待领域专家确认的 GateFlow/DQA 对象”，类型、资格、状态机和字段不变量未知。

下表每行适用于 Requirement；受管 Part、GateFlow/DQA 对象需能力声明后适用。非受管 Part 的每个工作集请求均返回“不支持该类型/未接入”，由 PLM 正常管理其内容，不自动分配 Variant 或触发 COW。四 BC 的具体拒绝规则必须由领域专家补齐，不能以抽象推演冒充四种业务规则已验证。

所有前置事实均为场景假设，除企业归属 AC-001 与下文 B04、B06、B09 的具体裁定外，证据为 Candidate；INV 编号也是候选。查询不强制发事件；异步事实需可靠交付和幂等消费。失败原因只在可信边界内完整区分，对用户的披露需权限政策裁定。

## B04 首次编辑的内容依据

**用户已确认**（本对话中对 B04 的明确答复）。子工作集从非共享 Tracker 派生一条 Requirement 时，标题为「初稿」。来源后来将标题改为「修订稿」。当子工作集首次编辑该条需求且只修改描述时，保存后标题仍为「初稿」，描述使用用户此次提交的值。首次编辑以派生时的内容为依据。

**来源彻底删除的分支也已由用户确认。** 如果子需求尚未发生本地写入时，来源工作集彻底删除原 Requirement，子需求仍然存在且可编辑。用户首次只改描述并保存后，标题仍是「初稿」，描述使用此次提交的值。

为兑现这个结果，完成来源删除前必须保证子需求仍能读取首次编辑所需的派生内容。历史版本或独立副本均可作为候选实现。保留期限、附件与关系覆盖范围，以及历史意外不可用时的处理方式待裁定。关联 [D3 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。

## B06：ALM Requirement 的合并拒绝

**用户已确认**（本对话中对 B06 场景的明确答复）。合并选择应用到目标 Requirement 后若整体违反 ALM 的业务规则，由 ALM 校验整个对象并决定是否提交。ALM 拒绝时，目标 Requirement 保持原样。Working Set 保留用户的字段选择和拒绝结果，该条合并仍未完成。

裁定范围是 ALM Requirement 的这条合并路径。关联 [D1 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。

## B09 接受字段时取源端最新值

**用户已确认的业务政策。** 用户审阅源端标题「修订稿」后选择接受该字段。提交前源端将标题更新为「定稿」，目标端未变。后端执行合并时读取源端该字段的最新值，目标校验通过后，目标标题为「定稿」。源端值更新本身不要求用户重新审阅。适用范围是用户已选接受且仍能定位的字段。确认来源为本对话中用户对该场景的明确裁定。

**目标同字段在提交前被修改的分支也已由用户确认。** 另一位用户在提交前修改了目标端同一个标题。执行合并时，目标整体校验通过后，用源端最新的「定稿」覆盖该目标标题，无需提示字段冲突或重新审阅。

**单字段不可读的兜底已由用户确认。** 当前业务场景下没有单个字段不可读的常规路径。若极端情况下执行时确实读不到已选字段，这条 Requirement 的合并保持未完成，批次继续处理下一条。

比较记录保留审阅时的「修订稿」。执行证据另记本次实际读取的源版本及应用结果，供回查。源字段删除的业务含义、读取与提交之间的并发处理，以及未知结果后的重试契约仍需明确。关联 [D4 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。
