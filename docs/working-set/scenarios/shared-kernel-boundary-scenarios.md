## PLM Part 共享查看（已确认）

- **Given** PLM 在默认工作集下管理承载 Part 的共享 Tracker。
- **When** 用户把该共享 Tracker 纳入其他工作集。
- **Then** 其他工作集可查看共享 Part 数据，PLM 在默认工作集管理其内容。该纳入不派生 Part，Part 不参与 Working Set 比对或合并。

依据见 [Part 接入范围](../domain/shared-kernel-boundary.md#plm-part-的接入范围用户已确认)。这是本对话用户的明确裁定。

## DQA 共享查看（已确认）

- **Given** DQA 自行管理技术评审任务、过程保证任务、问题报告 PR、检查单、检查单模板、批注、评审文档、评审报告，相关 Tracker 均为共享 Tracker。
- **When** 用户将这些共享 Tracker 纳入工作集。
- **Then** 用户可在工作集中查看共享数据，业务逻辑继续由 DQA 管理。DQA 的工作集结合点仅为纳入查看，不参与比对、合并或非共享派生。

依据为本对话用户确认，见 [DQA 范围](../domain/shared-kernel-boundary.md#dqa-共享查看范围用户已确认)。评审文档是被评审内容，评审报告是评审产物。B04—B10 的 COW/比对/合并路径不适用于 DQA。

## GateFlow 草稿版次内容替换

**状态为用户已确认的业务场景。** 来源是本对话中用户对 GateFlow Process 的明确说明。

- **Given** 一个 Process 有多个版次，每个版次对应一个工作集，父子工作集链条表达版次链路。叶子节点是可替换内容的草稿版次。
- **When** 用户在 GateFlow 中选择历史版次进行草稿内容替换。
- **Then** 从该历史版次取出全部内容数据，替换叶子草稿版次的内容。

用户进一步确认，在 V1 → V2 → V3（草稿）的链路中，用 V1 内容替换 V3 后，保留 V3 的版次身份、工作集 ID 与父级 V2，只替换 V3 的内容。V1 是此次内容来源。

**当前内容集合已由用户确认。** 若 V3 草稿新增了 V1 中没有的流程元素，用 V1 替换后，该元素从 V3 当前内容中移除，替换后的内容完整对应 V1。此处移除描述当前内容的成员变化。旧元素的物理清理、历史保留与外部引用处理仍需设计。

用户已确认 GateFlow 工作集只容纳固定四类业务对象：过程元素业务对象、裁剪问题、裁剪答案、合规映射，不纳入 Part 等共享 Tracker。历史替换围绕这四类业务内容进行。其内部细节业务逻辑属于 GateFlow 自身设计，本阶段聚焦与 Working Set 的范围、身份和整体切换协作。

用户本轮明确确认替换期间无需禁止编辑，整体覆盖符合业务语义。此确认更新历史 V4 内容替换 §7.1 暂停业务写入的候选政策，历史文档保留作为来源。

依据与历史候选见 [职责边界](../domain/shared-kernel-boundary.md#gateflow-process-与版次用户已确认)。用户已确认替换的原子可见性要求：准备期间 V3 继续使用当前完整内容，并允许用户正常编辑。全部准备成功后再整体切换为选定历史版次的内容，期间已保存的编辑允许被覆盖。某个元素准备失败时不切换，继续使用当前内容及期间已保存的编辑，不暴露部分准备结果。此处旧内容表示切换前仍可编辑的当前范围。具体重试、取消与切换瞬间的并发提交协议待设计。行为图见 [GateFlow 替换](../diagrams/collaboration-behavior.md#gateflow-草稿内容整体切换)。

## B04 首次编辑的内容依据

**用户已确认**（本对话中对 B04 的明确答复）。子工作集从非共享 Tracker 派生一条 Requirement 时，标题为「初稿」。来源后来将标题改为「修订稿」。当子工作集首次编辑该条需求且只修改描述时，保存后标题仍为「初稿」，描述使用用户此次提交的值。首次编辑以派生时的内容为依据。

**来源彻底删除的分支也已由用户确认。** 如果子需求尚未发生本地写入时，来源工作集彻底删除原 Requirement，子需求仍然存在且可编辑。用户首次只改描述并保存后，标题仍是「初稿」，描述使用此次提交的值。

为兑现这个结果，完成来源删除前必须保证子需求仍能读取首次编辑所需的派生内容。历史版本或独立副本均可作为候选实现。阶段 3.1 已确认附件、关系均固定为派生时状态，见 [SCN-012](core-scenarios.md#scn-012-派生附件与关系固定)。保留期限及历史意外不可用时的处理协议仍待设计。关联 [D3 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。

## B06：ALM Requirement 的合并拒绝

**用户已确认**（本对话中对 B06 场景的明确答复）。合并选择应用到目标 Requirement 后若整体违反 ALM 的业务规则，由 ALM 校验整个对象并决定是否提交。ALM 拒绝时，目标 Requirement 保持原样。Working Set 保留用户的字段选择和拒绝结果，该条合并仍未完成。

用户已进一步确认，参与 Working Set 的 PLM、GateFlow、DQA 对象同样采用此职责划分。各 BC 校验整个对象并决定是否提交，保留自己的校验规则；Working Set 管理合并选择、执行协调与结果记录。具体接入类型和各 BC 的真实校验场景待补充。关联 [D1 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。

## B08 部分成功与批次重试

**用户已确认的业务政策。** 一批合并中允许部分 Requirement 合并成功。A 已成功而 B 未完成时，用户点击重试只处理 B，保留 A 已成功的结果。即使 A 的源端在重试前再次变化，这次批次重试也跳过 A。

确认依据为本对话中用户明确答复「允许部分合并成功。确认重试只处理B，保留A已成功的结果」。关联 [D5 裁定进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。B10 的提交结果未知属于恢复协议待明确项，成功状态的可靠判定需在实现时验证。

## B09 接受字段时取源端最新值

**用户已确认的业务政策。** 用户审阅源端标题「修订稿」后选择接受该字段。提交前源端将标题更新为「定稿」，目标端未变。后端执行合并时读取源端该字段的最新值，目标校验通过后，目标标题为「定稿」。源端值更新本身不要求用户重新审阅。适用范围是用户已选接受且仍能定位的字段。确认来源为本对话中用户对该场景的明确裁定。

**目标同字段在提交前被修改的分支也已由用户确认。** 另一位用户在提交前修改了目标端同一个标题。执行合并时，目标整体校验通过后，用源端最新的「定稿」覆盖该目标标题，无需提示字段冲突或重新审阅。

**单字段不可读的兜底已由用户确认。** 当前业务场景下没有单个字段不可读的常规路径。若极端情况下执行时确实读不到已选字段，这条 Requirement 的合并保持未完成，批次继续处理下一条。

比较记录保留审阅时的「修订稿」。执行证据另记本次实际读取的源版本及应用结果，供回查。源字段删除的业务含义、读取与提交之间的并发处理，以及未知结果后的重试契约仍需明确。关联 [D4 评审进度](../reviews/2026-11-09-stage-3-architecture-review.md#裁定进度)。
