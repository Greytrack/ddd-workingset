> **修订**: v2.21 / 2026-10-27：审查与契约同步覆盖 00–09；统一分类记录比对、数据决定与处理确认、定向差异、处理确认和执行保护；文档对齐不代表实现风险关闭。

> **验证边界**: 本轮没有检查现网 Java 实现、数据库 DDL、线上数据、性能或运行中的事务/锁；下面的结论不是生产实现认证。

## 1. 总体结论

当前设计的核心方向合理，值得保留；功能主干已经形成，但尚不是完全闭合、可直接照单实现的规格。

| 维度 | 本轮判断 | 依据与限制 |
|------|----------|------------|
| 功能完备性 | 主干覆盖，闭环未完全覆盖 | 共享/派生、快照、解析、COW、删除、引用、Diff/Merge 已有模型；受管对象新建、回收站查询、替换/重挂、任务取消与恢复仍需细化 |
| DDD 合理性 | 总体符合项目的 DDD 叠加规则 | 业务 BC 保有自身行为，SK 定义稳定共享能力；LightTrackerItem 与本地业务实例的一致性责任仍未明确，锁不能代替聚合边界定义 |
| 架构合理性 | 对外较简洁，对内职责有依据 | TrackerItem/T、类型 SPI、Loader/Planner/协调器分工合理，Management 持有事务；历史读取、合并与恢复机制复杂度还未被完整封装和验证 |
| 架构优雅性 | 方向简洁，尚未达到实现上的成熟 | 已避免 TrackerBranch、有效条目包装类型和大 Tracker 聚合；不宜再增加对外概念，优先兑现现有少数契约 |
| 实施准备度 | 可做有界验证，不能直接认定生产就绪 | P0 来源切点、快照保留、写保护与确认协议；应先形成可执行验证，再扩展规模 |

“已明确”表示文档有可识别的业务约定；“待细化”表示接口、状态、并发或恢复责任尚未闭合；“未验证”表示本轮没有运行实现证据。三者不能互相替代。

当前最值得保留的设计：

- Tracker 同时承担目录与数据版本线身份，不再引入 TrackerBranch/BranchId。
- sharingMode 在创建时固化，Binding 不持有第二份共享策略。
- WorkingSet 是选择上下文，不是所有条目的整体事务容器。
- CommonId 标识实例族，LocalId 标识具体变体；派生身份先于物理内容分配。
- 业务代码使用 TrackerItem、Requirement、Bug 与对应列表；COW 和索引状态由内部管理。
- LightTrackerItem 是内部管理实体，与完整业务对象组合，而非业务对象替身。
- 内容端口由 BC 实现，实例化协调由 SK 实现，SK 不出现 Requirement/Bug/Part 的具体类型判断。
- 业务实体执行领域行为，SK 协调来源保护、持久化、索引同步与恢复；普通 Part 不承担工作集职责。

## 2. 功能覆盖与未闭合用例

对照 [03 核心用例](./03-use-cases.md) 和 [06 SDK/Demo](./06-tracker-item-java-demo.md)，不以“已有类名”代替“已有完整闭环”。

| 能力 | 当前覆盖 | 未闭合内容 / 验收重点 |
|------|----------|----------------------|
| Tracker 创建、共享复用与非共享派生 | 已明确 | 02 创建图仍让共享路径进入新索引生成；并发绑定/同族唯一约束的实际实现未验证 |
| WorkingSet 创建与扩展 | 已有受理、幂等步骤与 READY 发布 | 扩展现有 READY 工作集时如何隔离新 Binding，不影响旧条目可用性；失败、取消、资源与 pin 回收 |
| WorkingSet 编辑、重挂与替换 | Feature 层覆盖 | 重挂不应暗改 sourceTrackerId；替换的身份/子工作集/引用切换和旧集删除前置缺少完整协议 |
| 受管业务条目原生新建 | 只有身份规则与 provisionOriginal 工厂 | 缺创建用例和 SDK 协作：实体/索引/关系/Outbox 原子创建、权限、唯一字段、幂等与可见性 |
| 单条与强类型批量查询 | 已明确，已有 Demo | 来源切点、批量读一致性与错误分类需验证；搜索、分页、排序仍是另行定义而非已有实现 |
| 批量修改与自动 COW | 已明确，有界事务 Demo | 全部写路径接入、用户旧版本校验、意图校验、闭包规模限制与长任务恢复 |
| 显式 instantiate | 契约、Instantiator 和 Management 示例齐备 | 幂等、目标身份、事务完成释放、不保存入参修改；不能因此跳过后续写前闭包 |
| delete / undelete / delete2 | 生命周期与清理责任已明确 | 普通查询隐藏 DELETED，仍需回收站查询/选择入口；外部附件清理、保留冲突与重复请求结果 |
| Snapshot / HEAD | 时间戳语义、历史读取与 pin 前置已明确 | 多 Tracker 的提交可见性切点、索引/Binding/关系历史、长期保留、释放与失败回收 |
| 多级派生与来源扁平化 | 已规定指向已有物理来源 | 非版次对象的有效 source cut 如何保持，尤其是异步生成后的再次派生，见 R01 |
| 引用与跨工作集解析 | ownerLocalId + 逻辑目标已明确 | VIRTUAL 引用集合的历史读取与目标身份重建、引用独立变更的写入口、拒绝读取与 dangling 的外部表达 |
| 分类记录比对 / 属性合并 / 处理确认 | 业务主干已收敛 | 接受/拒绝与标记/不标记四组合、分类口径及内容冻结、结果与确认原子保存；按当前方向比较，不推断历史修改来源 |
| 合并轮次、徽章与审计 | 轮次状态和投影概念已有 | 分项成功不能提前宣布整个轮次完成；部分合并不得清空所有徽章；来源审计不等于 sourceLocalId |
| 普通业务对象与 BC 接入 | Part 路径和类型 SPI 已有 Demo | 真实 BC 的完整聚合加载、复制策略、能力注册和独立模块装配需联合验证 |

权限和工作流模型由外部团队所有，不要求本规格重新建模；但接入时机、目标权限、失败语义和同事务协作仍属于本规格需要明确的接口责任。

无需扩展为完整 ALM/PLM 产品规格，也无需给每个 Feature 增加新聚合；上述缺口优先通过现有用例、命令与端口闭合。

## 3. DDD 建模判断

### 3.1 Shared Kernel 与基础设施不是同一个概念

[00 战略定位](./00-overview.md) 中“业务 BC 可以强依赖稳定 SK 模型，SK 不反向感知具体业务模型”的方向合理。Shared Kernel 的关键是共同拥有和协同演进的领域子集，不是单纯放在 infrastructure 包中的通用工具。

建议区分三个面，但不必新增三个外部模块：

| 面 | 内容 | 消费者 |
|----|------|--------|
| 共享领域模型 | BusinessObject、TrackerItem、身份、Tracker/WorkingSet 的稳定语义 | 业务 BC |
| 公共应用能力与类型扩展端口 | 查询/命令、TrackerItemInstantiator、TrackerItemContentPort | 业务应用与 BC 集成适配作者 |
| 隐藏执行机制 | LightTrackerItem 的持久化布局、来源 Loader、COW 计划、lease/fencing、Job | SK 内部 |

“普通业务调用方不感知 COW”与“BC 的 SPI/内容端口作者理解快照读取和类型复制”不矛盾。不能要求扩展作者完全不了解其必须实现的存储协议，也不能把这些机制推给每个业务用例。

00 中对内部职责使用 Partnership、业务 BC 之间使用 Separate Ways 的名称可作为协作意图，但无需把同一内核内部模块宣称为独立 BC；实际已经通过 SK 关联的业务也不宜仅凭模式名称断言完全独立。架构边界以领域责任和依赖规则为准。

### 3.2 聚合、实体与一致性责任

| 概念 | 建议判断 | 应负责的不变量 |
|------|----------|----------------|
| Tracker | 目录/版本线聚合根 | 共享策略、来源关系、结构定义引用、生命周期；不包含全量条目事务 |
| WorkingSet | 工作上下文聚合根 | 名称、父子关系、Binding 选择与生命周期 |
| WorkingSetTrackerBinding | WorkingSet 内实体 | 有效选择、可见性与历史；来源图族级约束需要协调协议 |
| LightTrackerItem | 内部变体管理实体，保留 Entity 表达 | 身份、内容来源、存储状态、合法迁移；不是可以随意更新的普通查询索引 |
| Requirement/Bug 等 | BC 自有业务实体或聚合根 | 业务字段、状态机、完整聚合与业务不变量 |
| MergeRound | 轻量轮次聚合根 | 固定方向、发起人、时间与状态；不持有条目集合 |
| MergeEntry | 单条命令值对象 | CommonId、可信比较令牌和用户选择；执行结果可独立保存 |
| 定向差异 / MergeCheckpoint | 真实内容与最近处理状态分开管理 | 有效确认可使业务 EQUAL；跨轮次处理基准、false 取消及并发防线见 [09](./09-merge-domain-design.md#merge-model) |

LightTrackerItem 改称 Entity 可以保留，但 [01 §3.3](./01-domain-model.md) 中“由锁与数据库约束保障，所以不构成聚合边界”的因果关系不充分。聚合根本身也是实体；数据库锁不是聚合根与普通实体的判定依据。

建议明确：它不是独立公开业务聚合根；INSTANTIATED 时与该 LocalId 的本地业务内容、版次摘要及 Outbox 形成原子持久化一致性单元；VIRTUAL 时由工作集受管命令协调身份与来源状态。这里是内部责任说明，不要求新增包装对象，更不要求业务实体保存 LightTrackerItem 引用。

当前独立 LightTrackerItemRepository 可作为内部存储端口，但不得被普通 BC 当作另一个可直接保存的业务 Repository。Tracker、WorkingSet 负责各自不变量；血缘图和跨变体 COW 前置由明确协调协议负责。需要同步收紧 [00 §3](./00-overview.md) 中“各自一致性边界”和 [02 核心关系](./02-class-diagrams.md) 的解释。

项目允许 Management 协调跨 DataObject 原子副作用，因此不因跨实例 COW 直接判为违反 DDD，也不建议改用最终一致事件替代其前置保护。但它是有成本的跨实例一致性协议，不是一个可以无限扩张的聚合。

### 3.3 能力组合与领域行为

TrackerItem 直接被 Requirement/Bug 实现是合理依赖，不需要恢复 Adapter/有效条目包装层。共享身份与删除生命周期、Revisionable、Routeable 正交组合，也符合本领域要求。

跨聚合实例化已从实体移至 SK TrackerItemInstantiator：定位上下文显式传入，实体不注入服务或保存索引。实体保留只读 isInstantiated()，但旧观察值可能过时，不能充当直接保存或跳过闭包的依据。对外主路径仍是查询和受管命令，普通业务不用先显式实例化。

delete2 在实体上只校验删除意图，真正清理由协调器完成；应避免让调用者误以为直接对 detached 对象调用 delete2 已完成物理删除。BusinessObjectData 是内容交换表示，不应演变为取代各 BC 强类型模型的公共可变属性袋。

Long 标识符合 AirEdge 项目约定，无需为了形式上的 DDD 强制增加 Typed ID 类。真正需要的是身份校验、禁止不同职责混传、不可变来源和状态自校验。

## 4. 架构质量与复杂度控制

### 4.1 建议保留的职责链

业务 Management 持有事务，通过 SDK 进入 SK；SDKImpl 构建上下文，Planner 计算闭包，Loader 批量读确定来源，SK Instantiator 统一协调闭包，ContentPort 负责类型复制与内容读取/保存，LightTrackerItem 校验自身迁移，协调器原子保存索引与 Outbox。这条链条的每层都有职责，不必为了缩短调用链合并为万能 Service。

应用对象加载与存储协调不应伪装成“无 I/O 的纯领域服务”。01 已区分领域规则与协调，但其服务清单仍可按“纯策略/应用协调/类型端口/查询”解释，避免实现者把锁和存储塞进业务实体。

[项目架构规范](../../../.lattice/standards/architecture.md) 允许 SDKImpl 使用基础设施实现，但禁止 Biz 依赖 SDKImpl、组件互相穿透。SK 定义并实现实例化协调契约，BC 提供内容端口实现、Apps 装配注册表可以满足依赖倒置；实际 Maven/import 图本轮未验证。

### 4.2 当前不宜进一步抽象的部分

- 不新增 EffectiveItem 等对外结果类型；完整业务对象与内部管理实体已经分工。
- 不把 LightTrackerItem 公开引用塞进所有业务对象；内部上下文按 LocalId 批量关联。
- 不给 Tracker 增加全量条目集合的事务义务。
- 不在每个对象上增加 diff/merge 的不安全默认行为；类型比较/合并策略接入后再消费能力声明。
- 不为“索引 Entity 非聚合根”新增跨 BC 通用大聚合；先明确现有原子单元和命令边界。
- 不将日志、缓存、Outbox 的最终一致误当作来源保留、COW 或处理确认 的正确性保障。

### 4.3 优雅性取决于真实成本是否可控

轻量派生并不等于 O(1)：创建仍需枚举快照集合并生成 N 个身份索引，根写入可能实例化 M 个后代的完整内容。同 CommonId 血缘串行化也会限制兄弟变体并发。这是当前保守 COW 规则的代价，不是必须推翻该规则的理由。

建议声明索引批大小、闭包规模上限、来源去重与分页预算、长任务超时/取消、租约续期和积压监控。先测量再决定是否缩小保护粒度；不能仅凭“架构优雅”删掉正确性防线。

## 5. 优先风险与建议

P0 表示实现核心路径前必须闭合的正确性协议，不表示已经证实线上缺陷；P1 表示功能闭环/模型一致性应在相应用例上线前完成；P2 表示规模、演进或增强能力。

### R01 — P0：多级 VIRTUAL 派生必须保留有效来源切点

证据：[05 §2](./05-implementation-design.md) 规定来源扁平化；其存储只有 sourceLocalId/sourceRevision 和 Tracker.snapshot_at；[06 §6.1](./06-tracker-item-java-demo.md) 要求 capturedAt 是“有效内容切点”，但没有说明该切点从何处持久化或可靠重建。

可复现设计场景（非版次类型，revision=1）：

1. 10:00 受理从 A 创建 B，历史内容 v0 被 pin，尚未生成 B 索引。
2. 10:05 A 更新为 v1；此时 B 的索引尚不存在，历史保留支持后续读取 v0。
3. 10:10 B 的 Job 完成，B 仍为 VIRTUAL，来源是 A 的物理 LocalId，实际内容切点为 10:00。
4. 10:20 从 B 派生 C。C 应得到 B 在 10:20 的有效内容 v0，而不是 A 在 10:20 的 v1。

若扁平化后只复制 A 的 LocalId/revision=1，并无条件把 C 的 TrackerSnapshot=10:20 用作来源 cut，就会读取错误内容。后续 B 实例化并重置指针后，靠当前父索引也无法可靠恢复 C 当初的 cut。

建议让扁平化结果包含可复现的有效来源 cut：可选择内部保存 sourceCapturedAt/历史内容定位键，或从不可变、保留的索引历史确定性重建；本轮不替用户选择存储字段。多版次内容也需要保留成员、删除状态和关联历史。验收必须覆盖上述异步空窗加二次派生，而不只是单次 HEAD。

### R02 — P0：时间戳和受理 pin 不等于完整历史保留协议

证据：[01 Tracker 不变量](./01-domain-model.md)、[04 SQ1](./04-sequence-diagrams.md)、[05 §2](./05-implementation-design.md) 已有保留要求，因此它不是完全遗漏，而是尚未提供可验证机制。

保留应覆盖条目集合、Binding/索引、业务内容、删除状态以及业务需要的关系；只保留 Revision 内容不足以重现某时刻 WorkingSet。多 Tracker 共用时间戳也不自动保证同一个已提交可见性集合，需明确时态记录/提交可见性如何支持该 cut。

受理提交与 Job 投递应有可靠衔接。Provisioning pin 结束时，仍为 VIRTUAL 的条目和永久 Snapshot 所需历史不能一起释放；失败/取消后的 pin 回收也需规则。已有快照保留与 delete2 清除之间的冲突由 Specification/产品策略明确，不能同时无条件承诺两者。

建议把这些要求做成真实时态存储与保留协议的契约测试；不要求把成员列表永久逐项写入 Snapshot，也不认为 capturedAt 一个字段本身已经实现历史。

### R03 — P0：血缘写保护必须覆盖所有实际写入与操作意图

证据：[05 §4](./05-implementation-design.md) 与 [06 §7](./06-tracker-item-java-demo.md) 已明确同 CommonId 保护、fencing、CAS 和提交后释放，但 Guard/Repository 仍只是参考端口。

需要覆盖业务更新、delete/undelete/delete2、关系写入、checkIn、派生索引插入、Merge Add/Update/Delete 与后台 Job；索引 CAS 失败必须回滚已经写入的实体行。过期 fencing 校验必须落实到实际写入/提交防线，不能只在写前内存检查。

此前 Demo 的通用 executeAll 接受 INSTANTIATE，存在借任意回调绕过后代保护的入口。本次参考代码已收敛为只允许 CHANGE/RESTORE，INSTANTIATE 仅进入 SK 专用 Instantiator 并准备完整闭包；这关闭了示例的该入口，不等于现网所有写路径已验证。RESTORE 回调仍应限制为恢复意图，不能顺便编辑其他业务字段；真实事务、fencing/CAS 和旁路检查仍需测试证据。

所有写入口应要求有效 Management 事务；回调重入、跨 CommonId 补拿锁、远程副作用、实体逃逸应有禁止或明确约束。

### R04 — P0：比对合并专项风险

详细内容已迁入 [09 R04 风险与待验证项](./09-merge-domain-design.md#merge-review)，此处仅保留跳转入口。

### R05 — P1：补齐受管对象新建与回收站闭环

证据：[01 §3.3](./01-domain-model.md) 有原生身份不变量，[06 §5](./06-tracker-item-java-demo.md) 有 provisionOriginal，但 [03](./03-use-cases.md) 和 SDK 尚无受管对象新建用例。

新建应由业务 BC 执行创建规则，SK 确定目标 Tracker 与身份，原子建立业务实体、INSTANTIATED 索引、版次/关系与 Outbox；在子工作集新建也必须 commonId=localId，不生成祖先或已有后代的条目。请求重试需稳定幂等键，不能重复分配业务实例。

普通 resolve 隐藏 DELETED，undelete 虽已有命令，仍需回收站列表/详情/选择定位协议。delete2 的重复请求应明确返回已删除/不存在或幂等成功，而非依赖不可解释异常。

这些属于共享工作集功能闭环，不要求 SK 了解 Requirement/Bug 的创建字段。

### R07 — P1：Entity 表述需要一致性责任，而非纯技术索引解释

见 §3.2。LightTrackerItem 有稳定身份、生命周期和状态规则，Entity 判断合理；但它是正确性事实，不是可随时从查询投影重建的普通索引。

独立 Repository 和独立加载并不要求改回 AggregateRoot，却需要说明谁能修改、谁校验、在哪个原子单元保存。将它放回 Tracker 全量聚合会扩大锁竞争；完全交给裸 Mapper 又会丢失行为约束。建议保持内部 Entity + 受管命令 + LocalId 原子持久化责任。

### R08 — P1：Provisioning、重挂、替换和长任务尚未形成完整恢复状态机

证据：[03 F1.2/F1.5/F1.6](./03-use-cases.md)、[04 SQ1](./04-sequence-diagrams.md)、[05 §4](./05-implementation-design.md)。

WorkingSet 已存在不能作为整个 Job 已完成的条件；应按持久化步骤恢复。当前 SQ1 图的“工作集已存在则跳过”需要收紧。发布应校验预期的 Tracker/Binding/条目数量或稳定分页范围；仅“最后一个批次结束”不足以证明完整。

扩展既有工作集时，建议明确新增 Binding 的准备与发布边界；不能默默让全部既有条目不可用。重挂只改业务父关系，不改不可变来源；替换须明确子工作集如何处置，否则旧集可能因“有子集不能删除”而无法 Finalize。

长闭包需说明 lease 续期、崩溃接管、准备保留、取消后允许的状态与旧命令是否仍可提交。部分内容实例化可保留，但业务变更未执行的语义必须稳定。

### R09 — P1：引用专项风险

详细内容已迁入 [09 R09 风险与待验证项](./09-merge-domain-design.md#merge-review)，此处仅保留跳转入口。

### R10 — P1：schema、内容版本与编辑冲突需明确接入契约

Tracker 同时承载结构定义与版本线，派生应使用哪个 schema、FieldId 映射和复制策略需要由 sk-tracker-catalog/业务 BC 共同确定。工作流模型仍由 sk-workflow 所有；本规格只消费其版本/状态校验结果，不越界设计 Workflow。

sourceRevision=1 不能检测非版次内容变化。ContentVersion/摘要如何从 Store 返回、如何参与 Diff/CAS、是否排除纯实例化，需要具体端口合同。用户旧页面的 expectedVersion 不会因命令重新加载最新对象而自动检查；Demo 编辑命令当前没有该字段，正文提到它并不等于已经实现。

BC 还须明确业务编号唯一性、从属数据、附件共享/复制、权限归属以及完整对象加载范围。浅 Map 不等于聚合克隆。

### R11 — P1：工作集/Tracker 清理与 delete2 保留义务需要独立判断

WorkingSet 无子集不表示绑定 Tracker 无来源后代；无有效 Binding 也不表示没有 Snapshot、VIRTUAL 物理来源、冻结 Entry 或进行中命令依赖。

终止 Binding、软删工作集与实际 Tracker/条目清理应分阶段；清理时重新检查引用与历史义务，并与新派生/新绑定协调，避免“检查无引用后又被引用”的竞态。delete2 清理仅限当前 LocalId 的实体、历史与所属关系，不能按 CommonId 清族。

外部附件物理清理不能由本地 DB 回滚，需可靠清理状态和重试；成功定义应区分本地业务不可见与外部介质清除完成。不因“有 Outbox”就承诺已经清除了外部存储。

### R12 — P2：身份、审计、事件与投影需要避免错误承诺

CommonId 全局唯一的是实例族身份，同族变体合法重复持有它；LocalId 才是每个具体实例的唯一身份。旧审查 IT-ID-02 的“两个列全局唯一”表述已在本文件测试映射中纠正，不应生成 UNIQUE(common_id)。

CommonId + Tracker 来源图只保证存活族与拓扑追溯；sourceLocalId 实例化后重置为自身，不再保留逐次来源，Merge Add 也不等同于初次 Tracker 来源。完整历史审计属于另行定义的保留能力，并应与 delete2 清除要求协调。

LightTrackerItem 非公开聚合根之后，Outbox 中 aggregateId/aggregateVersion 可继续是通用信封名，但需明确对应 LocalId 的事件流和单调版本；delete2 最终事件在索引删除前捕获必要信息，不复制全部可恢复业务内容。幂等与拒绝倒序需按事件流键解释，不能把不同实例版本相互比较。

SHARED “立即可见”应表示提交后经权威查询可见，不意味着所有异步搜索/徽章缓存零延迟。若实例视图用于权威查询，必须参与同一读取协议；异步投影不能替代正确性数据源。

### R13 — P2：共享治理与公开 API 的稳定性

保留 BC 联合评审、能力注册和影响面清单。增强 Loader、pin、事件和恢复机制时，优先扩展内部合同，不给普通业务代码新增源指针/存储状态。

SDKImpl 注册扩展不应反向 import 组件实现；通过 SPI 与应用装配实现运行时协作。业务回调 API 适合进程内编排，不宜直接作为跨进程 REST 契约；若以后支持普通 load→save，再增加满足同等保护的 Unit of Work，而不是开放无条件 upsert。

## 6. 建议推进顺序与准入条件

| 阶段 | 最小交付 | 准入条件 |
|------|----------|----------|
| A：先收紧规格 | R01 来源 cut、R05 新建/回收站、R06 图文、R07 原子责任；将 01 矩阵与 04/05 对齐 | 同一用例不存在两种不同含义，新增内容不扩大外部 COW 负担 |
| B：验证 COW 正确性 | 一种 Revisionable 类型与一种非版次类型；两级派生、异步空窗、查询、instantiate、修改、删除与恢复 | R01–R03 的历史/并发/回滚测试可重复通过，所有写入口遵守同一协议 |
| C：闭合合并 | 双侧分类比对、数据/确认四组合、Add/Update/Delete/引用与并发；复核当前方向与双侧版本 | R04 及冲突矩阵通过；重试不重复签入/新增，不吞掉未处理差异 |
| D：完善流程与运营 | 扩展/重挂/替换、取消与恢复、保留/清理、Outbox 重放与监控 | 失败注入后可恢复；无泄漏 pin、孤立实例或错误轮次完成 |
| E：验证规模与迁移 | 身份分配、历史存储、Loader 批量预算、闭包上限、双读比对 | 性能与容量实测满足目标，迁移有校验和回滚机制 |

目前没有证据支持“功能全部完成”“完全符合严格单聚合模型”或“架构已达到生产最优”。更准确的结论是：核心概念选择合理，符合 AirEdge 的务实 DDD 方式；需要通过少数关键协议和用例闭环消除当前复杂度，而非继续增加模型层次。
